## Direction

Make the native conversation and composer primary, with a readable text measure and an explicitly opened IDE editor, diff, terminal or preview beside it. The Hermes design system calls for flat grouping, whitespace and sparse hairlines, consistent theme tokens, and no automatic navigation or focus changes when a tool produces output (`hermes-agent/apps/desktop/DESIGN.md:203`). Its desktop README describes a streaming transcript, structured activity, side-by-side previews and a file browser (`apps/desktop/README.md:193`). Its actual stack is Electron, React and a headless gateway; adapt the interaction to Haxeon rather than copying the technology (`apps/desktop/README.md`, “How it works”). The [Hermes product page](https://hermes-agent.nousresearch.com/desktop) presents the desktop as the agent outside the terminal.

## Exosuit starting point

`graphical/src/ui/CodexSessionPanel.hx` already implements queue/steer actions, approval requests, expandable reasoning and tool details, model and effort selectors. `graphical/src/ui/CodexMarkdownView.hx` uses Haxeon views and the editor's syntax registry with horizontally scrollable code and copy. `src/workspace/client/CodexMarkdown.hx` handles incomplete fences and limits external links to HTTP(S) and mailto; it is a small Markdown subset, so full fidelity should not be assumed.

## Recommended sequence and boundaries

1. Refine the existing native transcript and composer with shared theme tokens, accessible labels and reusable controls. Preserve focus, selection, scroll stability and readability in narrow docked panels.
2. Improve Markdown fidelity and exact copy, then connect file and change rows to existing IDE navigation and diffs. Verify long output, incomplete fences, links and scope labels.
3. Add image/file input only after proving clipboard, file picker and provider transport support. Preserve drafts and expose transfer state and failures; treat generated content as untrusted.
4. Add review, checkpoint and worktree actions when workspace services expose the needed semantics. A turn diff, a working-tree diff and a branch comparison answer different questions; conversation rewind does not imply external actions are reversed.

These are design recommendations, not claims that Exosuit or every provider already supports each feature.

## Exosuit attachment and artifact feasibility audit

This audit describes the current code in this checkout; provider support must be verified against each installed provider's actual protocol before enabling a capability.

**Image/file input.** `src/platform/HostFileDialogs.hx` exposes asynchronous `openFile` with multiple selection, so an attachment button can reuse the host chooser. `graphical/src/ui/UiImageTab.hx` loads local PNG, JPEG, BMP, GIF and TGA via `Image.loadFile`; `ImagePreviewView.hx` fits the decoded image and paints a transparency checkerboard. These are local-path views, not an attachment store or a remote upload. The UI clipboard bridge (`haxeon/packages/ui/haxe/haxeon/ui/core/ClipboardService.hx`) routes only `readText`/`writeText`. The NativeKit interface has `nk_clipboard_read_files` and `nk_clipboard_read_resources` as well as text (`haxeon/packages/platform/bindings/nativekit.hxi:3065`); it advertises an image format but exposes no image-byte read function there. Pasting image pixels requires an additive platform API and platform implementations, not just a composer handler. File-path clipboard support would still need event decoding and UI plumbing.

The send boundary is text-only: `WorkspaceAgentClient.agentAction` takes `text`; `WorkspaceAgentProtocol.AgentAction` has no attachment field, and `AgentInputMessage` stores text and fingerprint only. `CodexProvider.action` constructs a single text item for `turn/start` (`agent/src/workspace/provider/CodexProvider.hx:1241`); Claude sends `message.content = q.text` after write-ahead save (`ClaudeProvider.hx:310`); Pi's `startRun` and `sendPrompt` pass `{message: text}` (`PiProvider.hx:280`). Pi queued input has a text-derived fingerprint and strict durable size limits (`PiInputQueue.hx:21`, `:36`; `PiProvider.hx:344`). The local AgentKit provider also accepts text only (`AgentKitProvider.hx:447`). A generic image picker across Codex, Claude and Pi is therefore **a multi-layer feature**, not a small additive UI-only change; selecting a pathname does not make its bytes available on a remote workspace host, nor guarantee a provider will interpret the path as vision input.

A feasible phased path: (1) introduce capability-advertised typed attachments with stable IDs, MIME/type, size, and a content hash; preserve old text-only wire compatibility and reject unsupported providers explicitly; (2) stage bounded immutable bytes on the workspace host using a dedicated authorized transfer with quotas, cleanup and failure reporting, rather than trusting client paths or placing base64 in the 16 KiB Pi persisted record; (3) have each adapter translate staged data into its verified native protocol and test local and remote cases; (4) persist references and include hashes in queued-input fingerprints, recovery and cleanup so a retry cannot silently change content; (5) add chooser, thumbnail/remove controls and paste once the transport works. Limit accepted formats, byte count and decoded pixel dimensions before preview; maintain the draft on failure. Arbitrary files need their own explicit semantics: an attached immutable snapshot differs from a workspace-file reference. A narrower local-only, single-provider prototype may be smaller, but would still require verifying that provider's exact input schema, lifecycle and actual delivery; do not claim cross-provider parity.

**HTML/SVG artifacts (original audit).** `UiImageTab.supports` excludes SVG, and the current workbench routes supported local raster files to `ImagePreviewView` (`UiWorkbenchHost.hx:983`); ordinary HTML/SVG is therefore an editor file, not a rendered artifact. `haxeon/packages/platform/src/haxeon/platform/NativeKitWebView.hx` offers `create`, `setHtml`, bounds, visibility and disposal; the showcase `haxeon/packages/ui/examples/ui_showcase/components/WebViewSlot.hx` demonstrates a layout placeholder. At the time of the initial audit, the application had no integrated WebView artifact surface. The later Windows implementation and its limitations are recorded in [renderer contracts](renderer-contracts.md). The platform binding offers a navigation-policy flag and decision event (`nativekit.hxi:2934`, `:4180`), but this alone is not proof of script, network, file, subresource or process isolation. Do not feed model-generated HTML directly to `setHtml` as a safe preview.

Start with a code/artifact card offering copy and open-as-source. For visual SVG, add a bounded, sanitized, non-networking rasterization path and reuse the native image widget only after validating the parser/renderer and resource limits. For HTML, build an explicit user-opened preview pane only after a cross-platform isolation design prevents script/native bridge access, local file reads, external network/subresources and unsafe navigation; verify enforcement on every backend and define cleanup and failure behavior. If that isolation cannot be guaranteed, keep source-only preview. These were recommendations from the initial audit; see the later implementation and verification notes in [renderer contracts](renderer-contracts.md).


## Provider input parity follow-up

Read-only installed Pi RPC declarations (`@earendil-works/pi-coding-agent/dist/modes/rpc/rpc-types.d.ts`) and T3's local `packages/provider-pi/src/server/adapter.ts` confirm native base64 `ImageContent` on prompt/steer/follow-up. Exosuit's current Pi/Claude JSONL frames are limited to 256 KiB and queues to 1 MiB; the existing two 2 MiB Codex attachments would encode beyond those limits. Pi's durable outbox also stores text only. Enabling those controls requires combined encoded-payload preflight, bounded transport changes and durable attachment lease/queue semantics. That audit led to the subsequent Pi implementation: bounded 6 MiB byte framing and 8 MiB output queues, preflight before admission, durable opaque image references and restart/uncertainty tests. Pi image input is now negotiated. Subsequent read-only inspection of installed Claude 2.1.312 stream-JSON schemas established the actual image input shape; Claude now supports immediate image prompts with matching bounded byte transport and staged lease tests. Installed-version evidence is recorded in renderer-contracts.md.

Hermes's local `agent/anthropic_message_convert.py` shows Anthropic API image blocks, but this alone does not prove the installed Claude CLI accepts them through its stream-JSON protocol. No reference code was installed or executed. Claude/Pi full-response recovery now archives captured exact source rather than guessing identity from unpaged native history or branched JSONL records.
